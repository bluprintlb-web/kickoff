# Leader Sport — Context Handoff

## Project Overview
Custom-built football store website with two sides: a customer storefront and an admin dashboard (product/order/stock management, plus in-store POS). Products: kits/jerseys, trophies, balls, gloves, body/leggings, shin pads, grip socks (long & short), and normal socks. Store is based in **Lebanon**.

## Decisions Made
- Built custom (not a no-code platform like Shopify/WooCommerce) for full control.
- Architecture: single Next.js app — public storefront routes + a role-gated `/admin` section — rather than a monorepo with separate apps. Revisit only if the team/scale grows significantly.
- Stack:
  - Frontend: Next.js 16 + TypeScript (App Router)
  - Styling: Tailwind CSS v4 + shadcn/ui (built on **Base UI** — `@base-ui/react` — not Radix, in this shadcn version)
  - API: tRPC v11 (end-to-end type safety) + TanStack Query v5
  - Database: PostgreSQL
  - ORM: Prisma 7
  - Auth: Auth.js v5 (`next-auth@beta`) — Credentials provider, JWT sessions, Prisma adapter, `role` field (`CUSTOMER` / `ADMIN`)
  - Payments: **Whish Pay** (Whish wallet + Visa/Mastercard via their hosted checkout) — see "Payments" below, this is not fully wired up yet
  - Barcode scanning: `@zxing/browser` (camera-based, works cross-browser — no reliance on the experimental native `BarcodeDetector` API)
  - Image storage: Cloudinary (not yet wired up)
  - Hosting: Vercel (app) + Neon or Supabase (Postgres)
- Data model: `Product` → `ProductVariant` (SKU, size, color, barcode, stock, price override) to handle jersey sizes, sock length, glove sizes, etc. — not flat products.
- Sizing (`src/lib/sizes.ts`): three fixed size ladders, but each is now tied to *category* in the admin form (2026-07-13 change, at user's request — "sizes in jerseys only"), not just `ageGroup`:
  - `KIDS`: 20, 22, 24, 26, 28, 30 — only offered when Category = Jersey and "Mens or kids?" = Kids (`Product.ageGroup = KIDS`)
  - `ADULT` (mens): S, M, L, XL, XXL (2XL) — only offered when Category = Jersey and "Mens or kids?" = Mens (`Product.ageGroup = ADULT`)
  - `GLOVES`: 4, 5, 6, 7, 8, 9, 10, 11 — always offered when Category = Gloves, no age-group split (`Product.ageGroup` stays unset for gloves; the ladder is chosen by category alone in the form, not stored as a DB enum value)
  - Every other category (Trophy, Ball, Bodywear, Shin pads, Socks) has no fixed ladder — `ProductVariant.size` stays free text via a manual add/remove variant list, same as before.
- Mutations (signup/login/logout) use native `<form>` + Server Actions + `useActionState`, not react-hook-form — this is Next.js 16's own recommended pattern and avoids an extra dependency. Cart/checkout/POS/admin-product mutations use tRPC client-side mutations instead, since they're more interactive (dynamic rows, live scanning) than a one-shot form submit.
- Authorization is two-layered per Next.js's own security guidance: `src/proxy.ts` does a cheap, optimistic JWT-cookie check to redirect obviously unauthenticated/non-admin requests away from `/admin`; the real check happens in `src/lib/dal.ts` (`requireAdmin()`) and in `adminProcedure`/`protectedProcedure` (`src/server/trpc.ts`), called from every Server Action/Route Handler/tRPC procedure that touches sensitive data. Proxy alone is never trusted for security.
- Orders have a `channel` (`ONLINE` vs `IN_STORE`) and a `paymentMethod` (`WHISH` / `CARD` / `CASH`). `Order.userId` and the shipping fields are optional because POS/walk-in sales have neither.
- **Only one User can hold `role = ADMIN` at a time.** Enforced with a Postgres partial unique index (`CREATE UNIQUE INDEX ... ON "User" ("role") WHERE "role" = 'ADMIN'`), hand-written in `prisma/migrations/20260709230430_single_admin_constraint/migration.sql` since Prisma's schema DSL can't express a filtered unique constraint. Holds even against direct SQL/Prisma Studio edits, not just app code. Verified by actually trying to create a second admin and confirming Postgres rejects it. There's still no in-app way to *become* admin — it's a manual DB edit either way, this just makes it impossible to have two.

## Environment-specific corrections (discovered while scaffolding, 2026-07-09)
This project runs on **Next.js 16.2** and **Prisma 7**, both newer than typical training-data knowledge — the following diverge from older/common patterns and are easy to get wrong if "fixed" from memory:
- Next.js renamed `middleware.ts` → **`proxy.ts`** (exported function name `proxy`, or default export). `middleware.ts` is deprecated. Ours lives at `src/proxy.ts`.
- `params`/`searchParams`/`cookies()`/`headers()` are fully async now (must `await`) — no synchronous fallback left.
- Prisma 7's `prisma-client` generator (used here, output at `src/generated/prisma`) has **no `index.ts` barrel** — import from `@/generated/prisma/client`, not the bare `@/generated/prisma` directory.
- Prisma 7's `prisma-client` generator **requires an explicit driver adapter** — `new PrismaClient()` with no args throws a type error. We use `@prisma/adapter-pg` (`src/lib/prisma.ts`); swap to `@prisma/adapter-neon` later if you want Neon's HTTP-based edge driver instead of standard TCP.
- Prisma config (env var loading, migration path) now lives in `prisma.config.ts`, not `package.json`.
- zod is v4: use top-level `z.email()` instead of `z.string().email()`, and `{ error: "..." }` instead of `{ message: "..." }` for custom messages.
- Auth.js v5 type augmentation: augmenting `"next-auth/jwt"` for the `JWT` interface **does not merge** (it's a wildcard `export *` re-export that TS won't merge into) — augment `"@auth/core/jwt"` directly instead. `"next-auth"` augmentation for `Session`/`User` works fine (named re-export). See `src/types/next-auth.d.ts`.
- Env var names changed for Auth.js v5: `AUTH_SECRET` (not `NEXTAUTH_SECRET`).
- This shadcn/ui version generates components on top of **Base UI** (`@base-ui/react`), not Radix. Notably `Select`'s `onValueChange` can receive `null` (`string | null`, not just `string`) — every `onValueChange` handler in this codebase guards for that (`value && ...`).

## Gotcha: restart the dev server after editing `.env`
Next.js only reads `.env` when the dev server process starts — it does **not** hot-reload env var changes into an already-running `npm run dev`. If you change `DATABASE_URL` (or any other env var) and still see the old behavior, the fix is to stop and restart the dev server, not to change more code. This caused real confusion on 2026-07-09: the same `ECONNREFUSED` error kept showing up because the running dev server (from before `DATABASE_URL` was set) was never restarted.

## Gotcha: don't self-reference custom properties in the `@theme inline` block
`src/app/globals.css` had `--font-sans: var(--font-sans)` — a circular reference instead of pointing at the Geist font variable Next injects (`--font-geist-sans`, set via `layout.tsx`'s `geistSans.variable` on `<html>`). A self-referencing custom property is invalid CSS with **no build error and no console warning** — Tailwind's `font-sans` utility silently resolved to nothing and the whole site fell back to the browser's default serif font. Fixed 2026-07-10 (now `--font-sans: var(--font-geist-sans)`, matching the working `--font-mono: var(--font-geist-mono)` line right below it). If a future theme edit reintroduces unstyled/wrong-font pages with a clean build, check this block first — Tailwind won't error on it.
